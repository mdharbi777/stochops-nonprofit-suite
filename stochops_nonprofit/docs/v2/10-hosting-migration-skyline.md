# خطة الترحيل إلى Skyline Riyadh (داخل المملكة)

الهدف: نقل منصة الفاضل من الخادم المؤقّت (AWS Stockholm · t3.small 2GB) إلى **Skyline Riyadh 3**
(4 vCPU · 16GB RAM · 160GB NVMe · ~436 ريال/شهر شامل الضريبة) — بلا فقد بيانات، وبأقل انقطاع، ويحقّق
إقامة البيانات داخل المملكة. الحزمة تفوق خطّ الأساس في الدليل (4vCPU/8GB/150GB) بهامش مريح للتجربة وعدّة جمعيات.

> **أخطر نقطة:** يجب نقل `encryption_key` من إعداد الموقع الحالي كما هو — بدونه لن تُفكّ الحقول المشفّرة
> (رقم الهوية في المستفيدين/الموظفين، كلمات المرور). تُنقل عبر النسخة الاحتياطية الكاملة لإعداد الموقع.

## 0) قبل البدء (بلا انقطاع)
- [ ] خفض TTL لسجل DNS `alfadil.stochops.com` إلى 300 ثانية قبل يوم من التحويل (لتسريع التبديل).
- [ ] تأكيد أن Skyline يوفّر: وصول root/SSH بمفتاح، لقطات/Snapshots، ونسخاً احتياطياً داخل المملكة، وعنوان IP ثابت.
- [ ] أخذ نسخة احتياطية حديثة وكاملة من الخادم الحالي: `bench --site alfadil.stochops.com backup --with-files`
      (تُنتج database.sql.gz + ملفات public/private + site_config). الاحتفاظ بنسخة محليّة آمنة.

## 1) تهيئة خادم Skyline
- [ ] Ubuntu 24.04 LTS، تحديث النظام، إنشاء مستخدم غير جذري + مفتاح SSH، تعطيل دخول كلمة المرور.
- [ ] جدار ناري (ufw): يسمح 22 (SSH)، 80 و443 فقط.
- [ ] تثبيت Docker Engine + compose plugin، وتفعيل الخدمة.
- [ ] جلب مستودع frappe_docker + ملفات المشروع (compose + overrides + .env).

## 2) بناء/جلب الصورة المخصّصة
- [ ] بناء صورة التطبيق على الخادم الجديد بنفس الطريقة (BuildKit secret `apps_json` يحوي تطبيقنا فقط،
      + `CACHE_BUST`), **أو** نقل الصورة الحالية عبر `docker save | ssh | docker load` لتوفير وقت البناء.
- [ ] نفس إصدار الصورة (tag ثابت) لإمكان التراجع.

## 3) رفع الحزمة (بلا إنشاء موقع جديد)
- [ ] نسخ `.env` كما هو مع تعديل ما يلزم: `SITES=alfadil.stochops.com`،
      `SITES_RULE=Host(\`alfadil.stochops.com\`)`، بيانات MariaDB/Redis، بريد ops@stochops.com.
- [ ] تشغيل الحزمة: `docker compose -f compose.yaml -f overrides/compose.mariadb.yaml -f overrides/compose.redis.yaml -f overrides/compose.https.yaml --env-file .env up -d` — دون `new-site` (سنستعيد).

## 4) ترحيل البيانات (الخطوة الحرجة)
- [ ] نقل النسخة الاحتياطية (database.sql.gz + ملفات + site_config) إلى الخادم الجديد.
- [ ] استعادة الموقع: إنشاء الموقع ثم
      `bench --site alfadil.stochops.com restore <database.sql.gz> --with-public-files <pub.tar> --with-private-files <priv.tar>`.
- [ ] **التأكد من تطابق `encryption_key`** في `sites/alfadil.stochops.com/site_config.json` مع الأصل
      (يأتي ضمن نسخة الإعداد). اختبار: كشف رقم هوية مستفيد/موظف يعمل بعد الاستعادة.
- [ ] `bench --site alfadil.stochops.com migrate` ثم `clear-cache`، وتأكيد وجود Administrator والبيانات (عدّ السجلات).

## 5) تحويل DNS وHTTPS (نافذة الانقطاع القصيرة)
- [ ] توجيه A record `alfadil.stochops.com` إلى IP خادم Skyline.
- [ ] Traefik يطلب شهادة Let's Encrypt تلقائياً بعد انتشار DNS (للتحقق من الملكية).
- [ ] التأكد من HTTPS صحيح وتجديد الشهادة مُفعّل، وفرض HSTS.

## 6) التحقّق بعد التحويل (اختبار دخان)
- [ ] دخول demo/إداري، لوحة التشغيل، قوائم/تفاصيل، اعتماد محوكم، تصدير Excel/PDF، التهيئة، المركز القانوني.
- [ ] كشف رقم الهوية يعمل (دليل سلامة `encryption_key`), وسجل الاطّلاع الحسّاس يسجّل.
- [ ] العزل بين الجمعيات سليم، والمجدول نشط.

## 7) النسخ الاحتياطي والتعافي (على الخادم الجديد)
- [ ] تفعيل النسخ اليومي + **نسخ خارجي مشفّر داخل المملكة** (تخزين منفصل/Snapshots)، واختبار استرجاع فعلي.
- [ ] توثيق RPO/RTO ودليل الاستعادة.

## 8) الإغلاق والتراجع
- [ ] إبقاء خادم AWS يعمل (مُجمّداً) حتى انقضاء نافذة تحقّق (24–72 ساعة) قبل إيقافه.
- [ ] خطة تراجع: إعادة توجيه DNS إلى AWS إن ظهر خلل جوهري (ولهذا خفضنا TTL مسبقاً).
- [ ] بعد التحقّق: إيقاف/حذف موارد AWS، وتحديث سجلّ المعالجين ومواقع المعالجة (الإقامة الآن داخل المملكة).

## 9) بعد الاستقرار
- [ ] فصل بيئة staging عن الإنتاج، تدوير الأسرار (Administrator، مفاتيح)، إزالة حسابات/بيانات العرض (demo.admin ووسم «عيّنة»).
- [ ] مراقبة التوفّر والأخطاء وصحّة المجدول.

> ملاحظة سعة: 16GB NVMe مريحة لقاعدة MariaDB وعدّة جمعيات؛ عند نمو المرفقات يُنظر لفصلها في تخزين كائنات لاحقاً.
> هذا الترحيل بنية تحتية فقط؛ لا يفتح بوابة الإنتاج ولا ينشر نصوصاً قانونية — تلك خطوات منفصلة (docs/v2/09).
