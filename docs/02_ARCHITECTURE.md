# 02 — المعمارية (ARCHITECTURE)

## المبدأ العام
تطبيق Frappe مخصّص واحد (`stochops_nonprofit`) يُثبَّت على **موقع Frappe مستقل لكل جمعية**. لا multi-tenant داخل قاعدة واحدة، ولا `Charity` DocType متعدد العملاء في المرحلة الأولى.

```
┌─────────────────────────────────────────────┐
│  تطبيق واحد: stochops_nonprofit (مشترك)       │
└───────────────┬─────────────────────────────┘
        يُثبَّت على مواقع مستقلة
   ┌────────────┼────────────┐
   ▼            ▼            ▼
site: ekhlas  site: charityB  site: charityC
(DB+أسرار+   (DB+أسرار+     (DB+أسرار+
 مرفقات+نسخ)  مرفقات+نسخ)    مرفقات+نسخ)  ← كلها مستقلة تماماً
```

## لماذا موقع لكل جمعية؟
- يمنع تسرّب البيانات بين المستأجرين دون بناء نظام صلاحيات multi-tenant معقّد.
- نسخ احتياطية واستعادة مستقلة لكل جمعية.
- أبسط وأأمن للـ MVP.

## المكوّنات (من Frappe، لا نعيد بناءها)
- **DocTypes** لنماذج البيانات (الوحدة 1 والوحدة 2).
- **Roles + User Permissions** للصلاحيات (خادمية).
- **Frappe Reports / query / script reports** للوحدة 3 (لا جداول موازية).
- **Scheduler** للإشعارات داخل التطبيق.
- **Attachments (Private)** للمحاضر والأدلة، محكومة بالصلاحيات.
- **Version/Audit** لتتبّع التغييرات.

## ما لا نبنيه
React/Next.js، backend إضافي، microservices، Kubernetes، نظام تفويض موازٍ، محرك استيراد خاص، vector DB، multi-agent/RAG.

## الإعدادات لكل موقع — `Nonprofit Settings` (Single DocType)
الاسم الظاهر للجمعية، الشعار (إن كان مأذوناً)، المنطقة الزمنية Asia/Riyadh، صيغة التواريخ، لغة الواجهة، بيانات التواصل الداخلية، مفتاح `ai_enabled=false`.

## طبقة AI (مؤجّلة — Sprint 6)
واجهة قابلة للاستبدال `AIProvider.generate_summary(context, task_type)` مع `MockAIProvider` محلي أولاً. لا اتصال بمزود ولا مفتاح قبل موافقة مكتوبة. لا يُسمح للـ LLM باستدعاء وظائف تعديل قاعدة البيانات — نص مقترح فقط.

## الالتزام بالـ scaffold
يُلتزم بالهيكل الفعلي الذي يولّده `bench new-app` للإصدار المعتمد (`hooks.py`, `modules.txt`, `patches.txt`, `pyproject.toml`, بنية `doctype/`…). **لا تُفبرَك هذه الملفات يدوياً** لمجرد مطابقة مخطط توضيحي.
