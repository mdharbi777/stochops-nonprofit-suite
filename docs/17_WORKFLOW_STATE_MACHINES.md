# ١٧ — آلات الحالات ونضج التدفّقات (Workflow Maturity)

> الغرض: توثيق آلة الحالات المفروضة خادمياً لكل خدمة ذات حقل `status`، وبوابات الرقابة
> المالية (الصرف، وفصل الصرف عن الاعتماد)، وإبراز رسائل المنع في الواجهة.
> المبدأ الحاكم: **الخادم مصدر الحقيقة** لكل انتقال حالة. تُفرض القيود عند تغيير الحالة
> لسجل **قائم** فقط؛ الإدراج الأوّلي (البذور/الترحيل) غير مقيّد. الإعفاء الوحيد مشغّل
> المنصّة (`System Manager` — كسر الزجاج)، ويبقى مُسجّلاً عبر «سجل التغييرات».

المحرّك المشترك: [`stochops_nonprofit/governance.py`](../stochops_nonprofit/governance.py) →
`guard_transition(doc, allowed, disburse_states=None, disburse_label, payer_separation=False, approver_field="approved_by")`.
الحالة النهائية = مجموعة انتقالات فارغة `{}` (لا خروج منها لغير المشغّل).

## ١) الرقابة المالية (المساعدة/الصرف/الشراء)

مسار موحّد: **مقدّم/مسودة → (قيد المراجعة) → معتمد → مصروف/مُنفّذ**، مع:
- **فصل الواجبات:** لا يبتّ مُنشئ/مُقدّم الطلب في طلبه.
- **بوابة الصرف:** الانتقال إلى حالة صرف/تنفيذ يتطلّب صلاحية مدير الجمعية.
- **حدّ الاعتماد بالدور:** يتجاوز حدّ الجمعية (`expense_approval_limit`) يتطلّب تصعيداً للمشغّل.
- **البتّ موثّق ومختوم:** ملاحظة قرار مطلوبة + ختم خادمي (`approved_by` / `approved_on`).

### فصل الصرف عن الاعتماد (maker–checker–payer) — قابل للتفعيل
إعداد على مستوى الجمعية: `Charity.enforce_payer_separation` (Check، **معطّل افتراضياً**).
عند تفعيله: لا يُنفّذ الصرف/التنفيذ (الانتقال إلى حالة الصرف) **مَن اعتمد الطلب** —
أي يجب أن يكون الصارف غير المُعتمِد. يُطبَّق على: Assistance Request / Expense Request /
Procurement Request. معطّل افتراضياً حتى لا تُلزَم الجمعيات الصغيرة بثلاثة مستخدمين.

| الخدمة | المسار | حالة الصرف | نهائية |
|---|---|---|---|
| Assistance Request | مقدم → قيد المراجعة → معتمد → مصروف (أو رفض/إلغاء) | مصروف | مرفوض، مصروف، ملغى |
| Expense Request | مسودة → مقدّم → قيد المراجعة → معتمد → مصروف | مصروف | مرفوض، مصروف، ملغى |
| Procurement Request | مسودة → مقدّم → قيد المراجعة → معتمد → مُنفّذ | مُنفّذ | مرفوض، مُنفّذ، ملغى |

ملاحظة التصميم: بعض الخدمات تسمح بإعادة الفتح أو الاستعادة عمدًا (التزامات متكرّرة،
حوادث قد تُعاد، أرشفة قابلة للاستعادة). القيمة الحوكمية هي **تجميد الحالات النهائية**
(ملغى/مرفوض/مكتمل حيث ينطبق) ومنع القفزات غير المشروعة، لا تضييق التشغيل المشروع.

## ٣) رسائل البتّ/المنع في الواجهة (Axis 2 — إصلاح الفشل الصامت)

كانت واجهة `/nos` تبتلع رسالة الخطأ من الخادم عند منع انتقال حوكمي (شريط مؤقّت ٣ ثوانٍ
وسط الأعلى يُفوَّت بسهولة، مع مسح النموذج). أُصلح في
[`public/nos/nos-detail.js`](../stochops_nonprofit/public/nos/nos-detail.js) و
[`applications-ops.js`](../stochops_nonprofit/public/nos/applications-ops.js) و
[`nos-list.js`](../stochops_nonprofit/public/nos/nos-list.js):
- **تنبيه ثابت بارز** (`.ds-alert--err`) يُظهر سبب المنع عند الإجراء نفسه ولا يختفي تلقائياً.
- **شريط الخطأ لا يُغلَق تلقائياً** (يُغلق بالنقر) ويبقى النموذج وملاحظة القرار كما هي، والزر يُعاد تفعيله لإعادة المحاولة.
- تقييد المدخلات: درجات التقييم تُقصّ ضمن [0، الحدّ] (ملاحظة #4)، والمبالغ/الأعداد ≥ 0 في الواجهة (مع الفرض الخادمي القائم).

## ٤) تذكيرات الحالات العالقة (Axis 3)
تُضاف عبر [`setup/notifications.py`](../stochops_nonprofit/setup/notifications.py) كإشعارات
«Days After» على الموعد للحالات غير المنتهية: طلب حق متأخر، مبادرة تجاوزت نهايتها دون إغلاق،
إذن إفصاح انقضى دون إنهاء — إضافةً للتذكيرات القائمة (قرار/مهمة/التزام/حادثة 72 ساعة).
