# 00 — النطاق والافتراضات (SCOPE) — الإصدار 2.0

> **منصة الفاضل** — إدارة الجمعيات الخيرية بطريقة أسهل وأبسط، وحوكمة مرنة وعالية.
> مثبّت بقرار المالك (19 أكتوبر 2026). **هذه الوثيقة هي مرجع النطاق الملزم، وتَجُبّ استثناءات الإصدار 1.0** في [00_SCOPE](00_SCOPE.md) القسم 3. ما لم تُعدّله هذه الوثيقة من الإصدار 1.0 يبقى سارياً (خصوصاً مبادئ الانضباط). أي خلاف يُحسم لصالح هذا الملف.

---

## 1. هوية المنتج
- **الاسم التجاري الظاهر:** «منصة الفاضل».
- **الاسم التقني:** تطبيق Frappe مخصّص `stochops_nonprofit` (لا يتغيّر لتفادي كسر الترحيلات).
- **الطبيعة:** منتج SaaS متعدّد الجمعيات لإدارة عمليات الجمعيات الخيرية وحوكمتها — عربي RTL أولاً.
- **البريد التشغيلي:** `ops@stochops.com` (قائم ومُستخدَم عبر منتجات STOCHOPS ومنها «رصد») — يُستخدم كمُرسِل رسائل النظام.
- **المستخدم المستهدف:** الإدارة التنفيذية، منسّقو اللجان والبرامج، المالية، الموارد البشرية، الحوكمة في الجمعية.
- **التحوّل:** من أداة حوكمة خفيفة (٣ وحدات) إلى منصّة متكاملة لإدارة الجمعية. يُبنى التوسّع **وحدة-بوحدة ببوابات قبول**، لا دفعة واحدة.

## 2. ما يبقى ثابتاً من الإصدار 1.0 (مبادئ انضباط لا تُخالَف)
1. **وحدة واحدة قيد العمل في أي لحظة**، ولا تبدأ التالية قبل اجتياز اختبارات وقبول السابقة (Gate).
2. **صفر إنفاق** بلا موافقة مكتوبة صريحة: لا خدمة مدفوعة، ولا API بمقابل، ولا استضافة، ولا SMS/بريد مدفوع.
3. **الصلاحيات تُفرض على الخادم** (قوائم/سجلات/تقارير/تصدير/روابط/مرفقات)، لا بإخفاء أزرار الواجهة.
4. جميع الأرقام من queries/DocTypes، **لا من إجابات LLM**.
5. **الأفضل الإلغاء/الأرشفة** بدل الحذف النهائي؛ والحذف الحسّاس بدور إداري فقط مع سجل تدقيق.
6. القيمة غير المتوفّرة **«غير متوفّر» لا صفر**؛ التأخير صفة مشتقّة لا تُخزَّن؛ التوقيت Asia/Riyadh.
7. **لا ادّعاء عمل لم يُنفَّذ** (يُكتب `NOT RUN` وسببه)، ولا ادّعاء اعتمادات حكومية/شراكات رسمية.
8. لا تكرار لما توفّره Frappe أصلاً (مستخدمون، أدوار، مرفقات، سجلات تغيير، تقارير، تنبيهات).
9. لكل وحدة Definition of Done (القسم 8) وتقرير تسليم موثّق.

## 3. نموذج تعدّد الجمعيات (يَجُبّ القسم 6 من الإصدار 1.0)
- **منصّة واحدة متعدّدة المستأجرين**: كيان `Charity` + حقل `charity` على كل بيانات التشغيل، مع عزل مفروض على مستوى الاستعلام والسجل (`permission_query_conditions` + `has_permission` + `set_charity`). **مُنفّذ ومُختبَر.**
- تسجيل ذاتي باسم الجمعية + حتى ٥ حسابات بأدوار مختلفة لكل جمعية (قابل للزيادة بقرار المنصّة).
- العزل بين الجمعيات **شرط أمان حَرِج** — يُختبر A-لا-يرى-B في كل وحدة جديدة عبر UI/API/تقرير/تصدير.

## 4. خريطة الوحدات الكاملة
> لكل وحدة: حدود داخل/خارج النطاق صريحة. الوحدات الحساسة (المستفيدون/المالية/المانحون/الموارد البشرية) لا تبدأ قبل اعتماد [تصميم PDPL](11_PDPL_DESIGN.md) وبند معالجة البيانات (DPA).

### مُنجَز (الأساس)
- **القرارات واللجان** · **البرامج والمبادرات** · **المؤشرات والتقارير** — مكتملة ومختبَرة (الإصدار 1.0).
- **الواجهة المبرندة + التسجيل + الحسابات + الإعدادات + عربي-فقط + الدليل** — مكتملة.

### N1 — الأساسيات التشغيلية (استكمال)
- **داخل النطاق:** اسم «منصة الفاضل» على كل الواجهات؛ ربط `ops@stochops.com` كمُرسِل (تأكيد التسجيل/الإشعارات)؛ مراجعة الأدوار والصلاحيات؛ توحيد صيغ التواريخ الهجري/الميلادي عند الحاجة.
- **خارج النطاق:** لا SMS/واتساب.

### N2 — إدارة المستفيدين وطلبات المساعدة  *(حسّاسة — تتطلب PDPL + DPA)*
- **داخل النطاق:** سجل مستفيد (بيانات تعريف أدنى)، طلب مساعدة بحالة ومسار اعتماد، ربط الطلب بمبادرة/لجنة، مرفقات خاصة محكومة الصلاحية.
- **خارج النطاق:** صرف نقدي فعلي أو تحويل أموال؛ تقييم استحقاق آلي؛ بوابة خارجية للمستفيد في هذه المرحلة.
- **ضوابط بيانات:** رقم الهوية والبيانات الأسرية/الاجتماعية = **بيانات حسّاسة** (التصنيف أدناه) — تشفير وحجب وتقييد وصول صارم.

### N3 — المتبرعون والمانحون والمنح  *(حسّاسة — تتطلب PDPL + DPA)*
- **داخل النطاق:** سجل متبرّع/مانح، تعهّد/إيصال تبرّع (**تسجيل** مبلغ ومرجع، لا معالجة دفع)، منحة بشروطها ومصروفاتها وتقاريرها المرتبطة بمبادرة.
- **خارج النطاق:** **بوابة تبرّع/دفع إلكتروني** (لا مرور بطاقات/حوالات داخل المنصّة)؛ المقاصّة البنكية.

### N4 — المصروفات والموافقات والرقابة المالية  *(حسّاسة)*
- **داخل النطاق:** طلب مصروف/أمر صرف بمسار اعتماد متعدّد المستويات، ربط بميزانية مبادرة/منحة، حدود اعتماد حسب الدور، سجل تدقيق كامل، تقارير التزام.
- **خارج النطاق:** دفتر أستاذ محاسبي كامل/قيود مزدوجة؛ رواتب؛ تكامل بنكي للدفع. (يبقى رقماً إدارياً محوكماً، لا نظام محاسبة بديل.)

### N5 — التقارير المحكومة والالتزامات الحكومية
- **داخل النطاق:** قوالب تقارير حوكمة/أداء قابلة للتصدير (CSV/PDF)، لوحات التزام، تذكيرات بمواعيد الالتزامات (مثل تقارير الجهة المشرفة) **داخل النظام**.
- **خارج النطاق:** **تكامل API مباشر** مع منصّات حكومية حتى يُصرَّح به ويُتاح رسمياً (يُدرج حينها كبند مستقل باعتماد).

### N6 — الموظفون والمتطوعون والعقود والمشتريات  *(حسّاسة — HR)*
- **داخل النطاق:** سجل موظف/متطوّع (بيانات HR أدنى)، عقد بمدة وحالة وتنبيه انتهاء، طلب شراء/أمر شراء بمسار اعتماد ومورّد.
- **خارج النطاق:** رواتب فعلية/حماية الأجور؛ تكامل التأمينات؛ مناقصات معقّدة.

### N7 — استكمال المساعد الذكي والتكاملات الآمنة
- **داخل النطاق:** `MockAIProvider` محلي (مُهيّأ، موقوف افتراضياً)؛ حالات: مسودة قرارات/تلخيص حالة/مسودة تقرير — بمراجعة بشرية، بلا تعديل قاعدة بيانات، بلا بيانات مستفيدين.
- **خارج النطاق:** ربط مزوّد مدفوع (GATE AI) حتى إقرار سياسة البيانات والتكلفة؛ أي تكامل خارجي بلا موافقة الجمعية.

### N8 — الاستضافة السعودية والتشغيل الفعلي
- **داخل النطاق:** استضافة **داخل السعودية** يوفّرها المالك؛ staging ثم production منفصل؛ HTTPS؛ نسخ احتياطي/استعادة مُختبَرة؛ DPA موقّع قبل أي بيانات فعلية.
- **خارج النطاق:** اعتبار GitHub استضافةً؛ إدخال بيانات فعلية قبل DPA واكتمال ضوابط PDPL.

## 5. حدود ثابتة تبقى سارية حتى في المنصّة الكاملة
- **لا حركة أموال فعلية** داخل المنصّة (لا بوابة دفع، لا تحويل، لا مقاصّة) — المنصّة **تسجّل وتحوكم**، ولا تنفّذ المعاملة المالية.
- **لا تكامل حكومي/بنكي مباشر** قبل تصريح رسمي واعتماد مستقل.
- **الذكاء الاصطناعي يبقى Mock** حتى GATE AI.
- **صفر إنفاق** قبل موافقة مكتوبة.
- **لا بيانات فعلية** (مستفيدين/مالية/موظفين) قبل اعتماد تصميم PDPL + DPA.

## 6. مبادئ الحوكمة («حوكمة مرنة وعالية»)
- أدوار قابلة للتوسعة فوق أدوار الأساس الأربعة؛ **فصل الواجبات** في المالية (مُنشئ ≠ مُعتمِد).
- **مسارات اعتماد** قابلة للضبط حسب النوع والمبلغ (المصروفات/المشتريات/طلبات المساعدة).
- **سجل تدقيق** لكل تغيير في الحالة/المسؤول/المبلغ/الاستحقاق (المستخدم + التاريخ).
- **تقارير محكومة** لا تكشف ما لا يحقّ للمستخدم رؤيته؛ تعريفات واضحة أسفل كل مؤشر.

## 7. تصنيف حساسية البيانات (مرتبط بـ[تصميم PDPL](11_PDPL_DESIGN.md))
| المستوى | أمثلة | المعالجة |
|---|---|---|
| **حسّاس جداً** | رقم الهوية، بيانات أسرية/اجتماعية، صحية، حالة مستفيد | تشفير + حجب + أدنى وصول + سجل + DPIA |
| **شخصي** | أسماء، تواصل، متبرّع، موظف، مبالغ فردية | أساس نظامي + تقييد دور + احتفاظ محدّد |
| **تشغيلي** | قرارات، مبادرات، ميزانيات إجمالية، مؤشرات | عزل بالجمعية + صلاحيات الدور |

## 8. التسلسل التنفيذي بالبوابات
| المرحلة | المحتوى | البوابة |
|---|---|---|
| أساس | الوحدات الثلاث + الواجهة + التسجيل | ✅ منجز |
| **وثائق v2.0** | هذه الوثيقة + تصميم PDPL + اعتماد المالك | **الحالية** |
| N1 | اسم الفاضل + البريد + مراجعة الصلاحيات | GATE N1 |
| N2 | المستفيدون وطلبات المساعدة | DPA+PDPL ثم GATE N2 |
| N3 | المتبرعون/المانحون/المنح | GATE N3 |
| N4 | المصروفات والرقابة المالية | GATE N4 |
| N5 | التقارير المحكومة والالتزامات | GATE N5 |
| N6 | الموظفون/المتطوعون/العقود/المشتريات | GATE N6 |
| N7 | استكمال AI + تكاملات آمنة | GATE N7 (+GATE AI) |
| N8 | الاستضافة السعودية والتشغيل | GATE N8 |

**Definition of Done لكل وحدة:** نماذج + تحقق حقول → صلاحيات خادمية + اختبارات عزل سالبة → نماذج/قوائم/تقارير مطلوبة فقط → اختبارات آلية + QA يدوي → seed وهمي → تحديث قاموس البيانات ودليل المستخدم → Commit/PR/ملاحظة إصدار → مراجعة البوابة.

## 9. حالة الوثيقة
مسوّدة v2.0 بانتظار **اعتماد المالك** بعد مراجعة [تصميم PDPL](11_PDPL_DESIGN.md). لا يبدأ بناء أي وحدة حسّاسة (N2–N4, N6) قبل اعتماد التصميم وتوقيع DPA للبيانات الفعلية.
