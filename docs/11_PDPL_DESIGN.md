# 11 — تصميم حماية البيانات (PDPL DESIGN) — منصة الفاضل

> يُكمّل [10_PRIVACY_SECURITY](10_PRIVACY_SECURITY.md) ويفصّله للنطاق الموسّع ([00_SCOPE_v2](00_SCOPE_v2.md)).
> **المرجع النظامي:** نظام حماية البيانات الشخصية السعودي (PDPL) ولائحته التنفيذية، إشراف الهيئة السعودية للبيانات والذكاء الاصطناعي (SDAIA).
> **قاعدة حاكمة:** لا تُدخَل أي بيانات شخصية فعلية (مستفيدين/مالية/موظفين/متبرعين) قبل اعتماد هذا التصميم + توقيع **بند معالجة البيانات (DPA)** بين الجمعية وSTOCHOPS. التطوير والاختبار ببيانات وهمية فقط.

---

## 1. الغرض
ضمان أن كل وحدة حسّاسة في منصة الفاضل (N2 المستفيدون، N3 المانحون، N4 المالية، N6 الموارد البشرية) تُصمَّم **بحماية البيانات منذ التصميم وافتراضاً** (Privacy by Design & by Default)، بما يوافق PDPL قبل أي تشغيل فعلي.

## 2. الأدوار النظامية
- **المُتحكّم (Data Controller): الجمعية** — تحدّد غرض ووسيلة المعالجة وتملك البيانات.
- **المُعالِج (Data Processor): STOCHOPS** — يعالج نيابة عن الجمعية ضمن تعليماتها وبموجب DPA.
- **DPA إلزامي** قبل الإنتاج: يحدّد الغرض، أنواع البيانات، مدة المعالجة، التدابير الأمنية، المعالجة من الباطن، الحذف/الإرجاع عند الإنهاء، والإخطار بالخرق.
- **تعدّد الجمعيات:** كل جمعية مُتحكّم مستقل؛ العزل التقني يمنع وصول جمعية لبيانات أخرى.

## 3. الأساس النظامي للمعالجة والموافقة
- تحديد **أساس نظامي** لكل غرض (تنفيذ أغراض الجمعية غير الربحية / مصلحة مشروعة / موافقة صاحب البيانات حسب الحالة).
- **المستفيد:** موافقة مستنيرة عند جمع بياناته حيثما لزم؛ وإذا كان قاصراً تُؤخذ موافقة وليّ الأمر.
- **حصر الغرض:** تُستخدم البيانات لغرض جمعها فقط (مثلاً بيانات طلب المساعدة لا تُستخدم للتسويق).
- **الشفافية:** إشعار خصوصية مختصر عربي يوضّح الغرض والاحتفاظ والحقوق عند نقطة الجمع.

## 4. جرد البيانات والتصنيف (حسب الوحدة)
| الوحدة | عناصر البيانات | التصنيف | أبرز الضوابط |
|---|---|---|---|
| N2 المستفيدون | الاسم، رقم الهوية، التواصل، بيانات الأسرة، الحالة الاجتماعية/المالية، المرفقات | **حسّاس جداً** | تشفير الهوية + حجبها + أدنى وصول + سجل اطّلاع + DPIA |
| N2 طلبات المساعدة | نوع الطلب، الحالة، المبلغ، الربط بمبادرة | حسّاس | تقييد دور + سجل تدقيق |
| N3 المتبرعون/المانحون | الاسم، التواصل، التعهّد/الإيصال، مبلغ | شخصي | أساس نظامي + تقييد دور + احتفاظ |
| N4 المالية | طلبات صرف، معتمِدون، مبالغ، مرفقات | شخصي/تشغيلي | فصل واجبات + سجل تدقيق كامل |
| N6 الموارد البشرية | بيانات موظف/متطوّع، عقود، مستندات | **حسّاس جداً** | تقييد شديد + تشفير + احتفاظ نظامي |

**ممنوع نهائياً:** جمع بيانات تتجاوز الغرض (data minimization)، أو حقول حسّاسة بلا حاجة مثبّتة.

## 5. مبادئ PDPL المطبّقة في التصميم
1. **التقليل (Minimization):** حقول الحد الأدنى فقط؛ لا رقم هوية ما لم يكن ضرورياً مُبرَّراً.
2. **حصر الغرض وحصر التخزين:** احتفاظ محدّد المدة لكل نوع ثم حذف/إخفاء هوية.
3. **الدقة:** إتاحة التصحيح؛ تتبّع آخر تحديث.
4. **السلامة والسرية:** تشفير أثناء النقل (HTTPS) وعلى المستوى الحقلي للحسّاس جداً؛ عزل المستأجرين.
5. **المساءلة:** سجل أنشطة معالجة (RoPA) لكل وحدة (القسم 11) + سجلات تدقيق.

## 6. حقوق صاحب البيانات وكيف يدعمها النظام
| الحق | الدعم في المنصّة |
|---|---|
| العلم/الإشعار | إشعار خصوصية عند الجمع |
| الوصول/الحصول على نسخة | تصدير سجلّ صاحب البيانات بصلاحية إدارية |
| التصحيح | تحرير محكوم + سجل تغيير |
| الحذف/الإتلاف | أرشفة ثم حذف محكوم بدور إداري + سياسة احتفاظ |
| الاعتراض/سحب الموافقة | تعطيل المعالجة/وسمها، دون حذف ما يلزم نظاماً |

## 7. إقامة البيانات ونقلها
- **الاستضافة داخل السعودية** (N8) — بيانات الإنتاج لا تغادر المملكة بلا ضمانات وموافقة.
- **لا نقل عابر للحدود** للبيانات الشخصية بلا أساس نظامي وضمانات (PDPL).
- **المساعد الذكي:** Mock محلي لا يرسل شيئاً خارجاً. أي مزوّد حقيقي مستقبلاً يحتاج تحديد منطقة معالجة + موافقة + **منع إرسال بيانات المستفيدين** نهائياً.
- **البريد `ops@stochops.com`:** رسائل النظام تحمل بريد المستخدم + رابطاً موقّعاً فقط — **بلا بيانات مستفيدين**؛ يُدرج مزوّد البريد في DPA كمعالِج من الباطن.

## 8. التدابير التقنية والتنظيمية
- **صلاحيات على الخادم** (RBAC) + **عزل مستأجرين** مفروض على الاستعلام والسجل (مُنفّذ ومُختبَر).
- **تشفير حقلي** لرقم الهوية والحقول الحسّاسة جداً (تخزين مشفّر، فكّ عند الحاجة بصلاحية)، و**حجب** في الواجهة/التقارير (إظهار آخر ٤ أرقام فقط).
- **مرفقات خاصة** (Private) محكومة الصلاحية — لا روابط عامة.
- **سجل تدقيق** للاطّلاع/التغيير على الحقول الحسّاسة.
- **أدنى امتياز:** لا يُستخدم Administrator للعمل اليومي؛ أدوار دقيقة + فصل واجبات مالي.
- **نسخ احتياطي مشفّر** مستقل لكل جمعية + **تجربة استعادة** قبل الإنتاج.
- **إخطار الخرق** (القسم 13) ضمن المدة النظامية.
- **لا أسرار في git**؛ أسرار عبر البيئة/secret manager.

## 9. رقم الهوية الوطني وبيانات القُصّر
- يُجمع رقم الهوية **فقط عند ضرورة مُبرَّرة**؛ يُخزَّن مشفّراً ويُحجب عرضه ويُقيَّد الوصول إليه بدور محدّد وبسجل اطّلاع.
- بيانات القُصّر (ضمن أسر المستفيدين) تُعامَل بحساسية أعلى: موافقة وليّ الأمر، أدنى بيانات، وصول مقيّد.

## 10. الاحتفاظ والحذف
- مصفوفة احتفاظ لكل نوع بيانات (تُحدَّد مع الجمعية): مدة التشغيل + مدة نظامية ثم حذف/إخفاء هوية.
- الحذف الحسّاس بدور إداري مع سجل؛ الأفضل الأرشفة قبل الإتلاف النهائي.
- عند إنهاء التعاقد: إرجاع البيانات للجمعية ثم حذفها من أنظمة STOCHOPS وفق DPA.

## 11. سجل أنشطة المعالجة (RoPA)
يُحدَّث لكل وحدة حسّاسة قبل بوابتها: الغرض · فئات أصحاب البيانات · فئات البيانات · المستلمون · مدة الاحتفاظ · التدابير الأمنية · أي نقل.

## 12. تقييم أثر حماية البيانات (DPIA)
**إلزامي قبل تشغيل** الوحدات عالية الخطورة (N2 المستفيدون، N6 الموارد البشرية، وأي معالجة واسعة لبيانات حسّاسة): توثيق المخاطر والتدابير والقرار قبل إدخال بيانات فعلية.

## 13. الإخطار بالخرق
إجراء موثّق: اكتشاف → احتواء → تقييم → إخطار الجمعية (المُتحكّم) والجهة المختصة ضمن المدة النظامية → معالجة ودروس مستفادة.

## 14. قائمة تحقق قبل الإنتاج (بوابة PDPL)
- [ ] DPA موقّع بين الجمعية وSTOCHOPS.
- [ ] إشعار خصوصية عربي عند نقاط الجمع.
- [ ] تشفير حقلي + حجب لرقم الهوية والحقول الحسّاسة جداً.
- [ ] أدوار وفصل واجبات مفروضة على الخادم + اختبارات عزل سالبة.
- [ ] سجل تدقيق للحقول الحسّاسة + سجل أنشطة معالجة محدّث.
- [ ] مصفوفة احتفاظ/حذف معتمدة.
- [ ] DPIA للوحدات عالية الخطورة.
- [ ] نسخ احتياطي مشفّر + تجربة استعادة ناجحة موثّقة.
- [ ] استضافة داخل السعودية + HTTPS + عدم كشف قواعد البيانات.
- [ ] منع وصول المساعد الذكي لبيانات المستفيدين.

## 15. حالة الوثيقة
مسوّدة بانتظار اعتماد المالك. تُفعَّل بنودها وحدةً-بوحدة: لا تبدأ وحدة حسّاسة قبل استيفاء ما يخصّها من هذه القائمة.
